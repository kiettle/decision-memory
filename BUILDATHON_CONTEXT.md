# DevSamurai Buildathon 2026 — Context for Codex

**Purpose:** Give Codex enough event context to make implementation and scope decisions for the Buildathon project without rereading the full event PDF.

---

## 1. Event Overview

**Event:** DevSamurai Vietnam Buildathon 2026  
**Overall dates:** 05/10/2026 → 18/11/2026  
**Theme:** Think → Build → Impact

This is an internal company product-building event. The goal is to start from a real problem, understand the target users, and turn the idea into something demonstrable and valuable.

The project does **not** need to be a complete production product. A convincing MVP/prototype/demo is enough if it clearly demonstrates the problem, the solution, and the user value.

---

## 2. What the Organizers Care About

The event explicitly prioritizes:

- a clear real-world problem;
- a clearly defined target user;
- a meaningful pain point;
- a solution that directly addresses that pain point;
- strong product thinking;
- a convincing end-to-end demo;
- practical value and impact.

The event does **not** reward technical complexity for its own sake.

Do not assume that more code, more frameworks, a more complicated architecture, or more features will score better.

### Important implementation implication

For this Buildathon:

> Prefer a smaller, polished, clearly valuable MVP over a larger but unfinished product.

When choosing between:
- adding another feature; or
- improving the core flow/demo/usability,

prefer improving the core flow.

---

## 3. Who Can Participate

- All employees may participate except Team Leaders and members of the judging panel.
- Participation can be solo or in teams of 2–4 people.
- A team does not need to include a developer.
- Each person may participate in only one main project.

---

## 4. Accepted Project Types

Accepted outcomes include:

- Web app
- Mobile app
- Jira Plugin
- Interactive MVP/prototype with a clear demo and product-value explanation

The product does not need to be related to DevSamurai’s current products.

---

## 5. Project Definition Requirements

Every project should answer:

1. **Problem** — What problem are we solving?
2. **Target User** — Who experiences this problem?
3. **Pain Point** — Why is this problem worth solving?
4. **Solution** — How does the product solve the problem?
5. **Value** — What value does the user gain?
6. **Demo** — How can we prove the solution works or demonstrate the experience?

Two suggested directions:

### Build for Our Company

Build something that makes work at DevSamurai better, for example by:
- saving time;
- reducing manual work;
- improving collaboration;
- reducing errors;
- making work more convenient.

### Build What You Wish Existed

Build something that solves a recurring problem in work or daily life, even if it is unrelated to current company products.

These are only idea prompts. All projects use the same scoring rubric.

# 14. Context for Our Project: Decision Memory

Our Buildathon project is:

## Decision Memory

### Core problem

Important decisions happen in Slack and other work tools, then become difficult to retrieve months later.

After 6–12 months:
- people may forget the exact keyword;
- they may not remember the Slack channel;
- the original thread may no longer be available;
- team members may have changed;
- similar decisions may exist for different services/features.

### Core product idea

Capture an important decision where it happens, preserve enough context independently, and make it easy to find later.

Core formula:

```text
Decision
=
What
+
Why
+
Where it applies
+
Evidence
```

### MVP flow

```text
Slack discussion
    ↓
Save as Decision
    ↓
Confirm structured Decision
    ↓
Persist durable context
    ↓
Decision Library
    ↓
Search / filters
    ↓
Open Decision
    ↓
Understand What + Why + Applies To
    ↓
See related Jira work
```

### MVP priorities

For the Buildathon, prioritize:

1. Reliable Slack capture.
2. Durable context independent from Slack.
3. Very low-friction Decision creation.
4. Search / filtering.
5. `Applies To` to distinguish similar Decisions.
6. Clear Decision detail page.
7. Related Jira link.
8. Superseded Decision history.
9. UI/demo polish.

### Explicit non-goals for the 3-week MVP

Do not implement unless specifically requested after core MVP is stable:

- Graph UI
- Neo4j / graph database
- Full Jira Forge Marketplace integration
- Bitbucket / GitHub integration
- Semantic/vector search
- Full AI knowledge assistant
- Microservices
- Kafka/event buses
- Complex role systems
- Enterprise analytics

AI-assisted Slack-thread extraction may be a stretch feature, but it must not become a dependency for the core MVP.

# 15. Implementation Guidance for Codex

When making implementation choices for this Buildathon:

### Prefer

- simple architecture;
- one backend;
- one primary relational database;
- focused UI;
- explicit business rules;
- fast end-to-end iteration;
- testable core flows;
- a polished demo path.

### Avoid

- premature abstractions;
- speculative extensibility;
- infrastructure that exists only to look impressive;
- implementing the post-MVP roadmap during the Buildathon;
- adding features that do not improve the main demo or core value.

### Decision rule

When uncertain whether to implement something, ask:

> Does this materially improve Problem & User Value, Product Thinking, or the end-to-end Demo within the 3-week MVP?

If not, defer it.

---

# 16. Buildathon Definition of Done

For this event, the project does not need to be production-complete.

It is ready for submission when:

- the core problem is clearly demonstrated;
- the target user is clear;
- the core flow works end to end;
- the MVP visibly solves the pain point;
- the demo is stable;
- the team can explain technical/product decisions;
- the 60–90 second video can communicate the product without lengthy explanation.

A smaller stable product is better than a larger unfinished product.
